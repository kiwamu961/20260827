## 1. 目的

本書は、物件写真をYOLOで検出し、検出結果をJavaScriptで分類してカテゴリ別に表示するプロトタイプの機能・非機能要件を定義する。プロトタイプのゴールは、写真のアップロードから分類結果の表示、手動修正までの一連の動作を確認できる状態にすることである。

## 2. サービス概要

利用者が1物件分の写真をまとめてアップロードすると、システムはYOLOで画像内の設備・家具を検出する。JavaScriptの分類処理は検出物と信頼度を基に、顧客が写真を探しやすいカテゴリへ分類する。利用者は分類結果を確認・修正し、自社サービスで利用できる状態にする。

## 3. 用語定義

| 用語 | 定義 |
| --- | --- |
| 物件 | 分類対象となる不動産の管理単位 |
| 写真 | JPGまたはPNG形式の分類対象画像 |
| 検出物 | YOLOが画像内から検出した設備・家具等の物体 |
| 信頼度 | YOLOが検出物を正しいと推定する確度 |
| 分類カテゴリ | 写真を整理する浴室等の表示単位 |
| 未分類 | 信頼度が低い、または判定ルールに該当しない写真の分類 |
| 自社運用実験 | プロトタイプを自社の物件写真で実際に利用し、効果と運用負荷を測定する期間 |

## 4. 対象ユーザー

| ユーザー | 利用目的 |
| --- | --- |
| 物件写真の登録担当者 | 写真をまとめて分類する |
| 物件を探す顧客 | 分類済みの写真から気になる場所を確認する |
| 自社の検証担当者 | プロトタイプの動作と分類結果を確認する |

## 5. スコープ

### 5.1 プロトタイプ対象範囲

- 複数のJPG・PNG写真を一括アップロードする。
- YOLOを用いて画像内の設備・家具を検出する。
- JavaScriptで検出結果と信頼度を分類カテゴリへ変換する。
- 7カテゴリと未分類へ写真を振り分ける。
- 分類結果、検出物、信頼度を画面に表示する。
- 利用者が写真の分類を手動修正する。
- 分類処理中の進捗と処理完了状態を表示する。

### 5.2 プロトタイプ対象外

- ユーザー登録、ログイン、権限管理
- 課金、契約、Normal・Proの料金切り替え機能
- 物件管理システム、不動産ポータルとの自動API連携
- 独自データによるYOLOモデルの追加学習
- 物件説明文やキャッチコピーの自動生成
- 顧客行動に基づく写真の表示順最適化
- 長期的な画像保管サービス
- 顔、ナンバープレート、表札等の個人情報自動マスキング

## 6. 機能要件

| ID | 機能名 | 要件 | 優先度 |
| --- | --- | --- | --- |
| F-001 | 写真アップロード | 利用者はJPG・PNG形式の写真を複数枚選択してアップロードできる。 | Must |
| F-002 | 入力チェック | 対応外の拡張子、破損画像、上限枚数超過を検出し、処理を開始せずエラー表示する。 | Must |
| F-003 | YOLO物体検出 | システムは各写真に対してYOLO推論を実行し、検出物の名称、矩形領域、信頼度を取得する。 | Must |
| F-004 | JavaScript分類 | JavaScriptは検出物と信頼度を入力として、写真を7カテゴリまたは未分類へ分類する。 | Must |
| F-005 | 分類カテゴリ表示 | システムはカテゴリ別の写真一覧を表示する。 | Must |
| F-006 | 判定根拠表示 | 各写真について、分類カテゴリ、信頼度、主な検出物を表示する。 | Should |
| F-007 | 手動修正 | 利用者は写真の分類先を別カテゴリまたは未分類へ変更できる。 | Must |
| F-008 | 一括確認 | 利用者はカテゴリごとの写真枚数と未確認写真を確認できる。 | Should |
| F-009 | 処理結果の破棄 | 利用者は処理完了後に結果を破棄できる。 | Should |
| F-010 | 処理状態表示 | 処理中、完了、失敗の状態と処理済み枚数を表示できる。 | Should |

### 6.1 分類カテゴリ

| カテゴリ | 主な検出物・判定根拠 |
| --- | --- |
| 浴室 | バスタブ、シャワー、浴室内設備 |
| トイレ | 便器、手洗い器、トイレ収納 |
| リビング | ソファ、テーブル、テレビ、窓 |
| 玄関 | 玄関扉、下足入れ、廊下 |
| キッチン | シンク、コンロ、冷蔵庫、キッチン収納 |
| 洗面所 | 洗面台、洗濯機置場、脱衣所 |
| バルコニー | 手すり、物干し竿、屋外床、眺望 |
| 未分類 | 信頼度不足、複数候補が同程度、または判定根拠なし |

### 6.2 分類ルール

- JavaScriptは、検出物ごとに定義したカテゴリ対応表を参照して分類する。
- カテゴリごとの信頼度が設定した判定閾値未満の場合は、未分類とする。
- 複数カテゴリの検出物がある場合は、カテゴリごとの信頼度を比較して最も高いカテゴリを候補とする。
- 同程度の候補が複数ある場合は自動確定せず、未分類として利用者の確認対象にする。
- 分類結果は自動確定ではなく、利用者が手動修正できる状態で表示する。
- 判定閾値と検出物・カテゴリ対応表は定数として管理し、プロトタイプ後に自社運用実験の結果を基に調整する。

## 7. プラン別利用制限

本プロトタイプでは料金計算・契約管理を実装しないが、本番サービスの利用制限は次を前提とする。

| 項目 | Normal | Pro |
| --- | --- | --- |
| 月額料金 | 10,000円（税別） | 50,000円（税別） |
| 月間処理写真数 | 3,000枚まで | 20,000枚まで |
| 1回のアップロード | 50枚まで | 100枚まで |
| 一括アップロード | なし | 200枚まで |
| 元画像保存期間 | 処理完了後7日 | 処理完了後30日 |
| 分類結果保存期間 | 30日 | 90日 |

上限超過時の追加料金と契約単位は、自社運用実験で実際の処理量とコストを確認した後に確定する。

## 8. 非機能要件

| 分類 | 要件 |
| --- | --- |
| 性能 | 自社検証用の標準的な物件写真を、アップロード後に順次処理し、処理中の進捗を表示する。厳密な処理時間目標は自社運用実験で測定して定める。 |
| 可用性 | プロトタイプは自社運用実験を目的とし、外部顧客向けSLAは設定しない。 |
| コスト | 画像処理基盤は複数物件で共有し、処理量上限を設ける。元画像はプラン別保存期間を過ぎたら削除する。 |
| ストレージ | 元画像と分類結果を分けて管理し、不要な元画像を長期保存しない。サムネイルや重複コピーの生成はプロトタイプで最小限にする。 |
| エラー処理 | 1枚の処理失敗で全体を停止せず、失敗した写真をエラー一覧に表示して他の写真を処理する。 |
| 保守性 | 分類カテゴリ、検出物対応表、信頼度閾値をJavaScriptの設定として変更できる構成にする。 |
| 拡張性 | 将来のAPI連携を妨げないよう、分類結果に物件識別子、写真識別子、カテゴリ、信頼度を含める。 |
| セキュリティ | 外部公開前にアクセス制御、通信保護、画像の保存期間、削除処理を別途定義する。プロトタイプは自社検証環境に限定する。 |
| 対応環境 | 自社で使用する最新のChromeまたはEdgeを優先し、プロトタイプでの対応ブラウザを限定する。 |

## 9. データ要件

### 9.1 写真データ

| 属性 | 内容 |
| --- | --- |
| photoId | 写真を識別する一時ID |
| propertyId | 物件を識別するID。プロトタイプでは入力値またはセッション単位で管理する |
| fileName | アップロード時のファイル名 |
| fileType | JPGまたはPNG |
| fileSize | ファイルサイズ |
| originalPath | 元画像の一時保存先 |
| resultPath | 分類結果の出力先 |
| status | queued / processing / completed / failed |
| category | 分類カテゴリまたは未分類 |
| confidence | 採用した分類の信頼度 |
| detectedObjects | 検出物の名称、矩形、信頼度 |
| corrected | 手動修正済みかどうか |
| createdAt | アップロード日時 |
| expiresAt | 自動削除日時 |

### 9.2 保存方針

- プロトタイプでは処理に必要な期間だけ画像を保存し、利用者が処理結果を破棄できるようにする。
- 本番想定ではNormalとProの保存期間を適用する。
- 自動削除に失敗したデータは運用実験で検知できるよう、削除予定日時と削除結果を記録する。
- 評価用画像には、可能な限り個人情報を含まない社内利用可能なデータを使用する。

## 11. ユースケース

### UC-01 写真を分類する

| 項目 | 内容 |
| --- | --- |
| アクター | 物件写真の登録担当者 |
| 事前条件 | 対応形式の写真を用意している |
| 基本フロー | 1. 物件識別子を入力する 2. 写真を複数選択する 3. アップロードする 4. YOLO検出とJavaScript分類を実行する 5. 分類結果を確認する |
| 代替フロー | 上限超過や非対応画像がある場合はエラーを表示し、対象写真を修正して再実行する |
| 事後条件 | 写真ごとにカテゴリまたは未分類が設定される |

### UC-02 分類を手動修正して確認する

| 項目 | 内容 |
| --- | --- |
| アクター | 物件写真の登録担当者 |
| 事前条件 | UC-01が完了している |
| 基本フロー | 1. 分類結果を確認する 2. 誤分類写真のカテゴリを変更する 3. 分類結果を保存する 4. 自社サービスで利用する |
| 事後条件 | 写真ごとの分類結果が保存され、カテゴリ別に表示できる |

### UC-03 分類結果の動作を確認する

| 項目 | 内容 |
| --- | --- |
| アクター | 物件写真の登録担当者 |
| 事前条件 | 対応形式の評価用写真がある |
| 基本フロー | 1. 複数写真をアップロードする 2. 処理状況を確認する 3. カテゴリ別の分類結果を確認する 4. 必要に応じて手動修正する |
| 事後条件 | 写真がカテゴリ別に表示され、分類結果を確認できる |

## 12. 開発制約とスケジュール

### 12.1 1.5日プロトタイプの工程

| フェーズ | 期間 | 完了条件 |
| --- | --- | --- |
| 企画確定 | 0.5日 | カテゴリ、評価用写真、分類ルールを確定する |
| プロトタイプ開発 | 0.5日 | アップロード、YOLO検出、JavaScript分類、カテゴリ表示、手動修正が動作する |
| 確認・検証 | 0.5日 | 分類結果の表示、手動修正、基本動作の確認が完了する |

### 12.2 コスト制約

- プロトタイプでは既存のYOLOモデルを使用し、追加学習のためのデータ作成・学習時間を発生させない。
- プロトタイプでは自社検証環境を利用し、常時稼働する専用GPUの構築を避ける。
- 画像保存期間とアップロード枚数を制限し、ストレージと転送量を抑える。
- カテゴリ分類はJavaScriptのルール処理から開始し、分類モデルの追加導入は自社運用実験後に判断する。
- Normal・Proの課金処理、外部API連携、個別カスタマイズはプロトタイプ後に実装する。

## 13. 受け入れ基準

- [ ] JPG・PNGの複数写真をアップロードできる。
- [ ] 対応外形式、破損画像、上限超過をエラーとして表示できる。
- [ ] 各写真に対してYOLOの検出結果を取得できる。
- [ ] JavaScriptの分類処理により、7カテゴリまたは未分類へ分類できる。
- [ ] 浴室、トイレ、リビング、玄関、キッチン、洗面所、バルコニーのカテゴリを画面で確認できる。
- [ ] 利用者が誤分類を手動修正できる。
- [ ] 分類結果をカテゴリ別に画面表示できる。
- [ ] 1枚の処理失敗が他の写真の処理を停止させない。
- [ ] プロトタイプの構築範囲が1.5日で完了可能な粒度に収まっている。
- [ ] 写真のアップロードから分類結果の表示、手動修正までの一連の動作を確認できる。

## 14. 未確定事項

- YOLOモデルの具体的な種類、ライセンス、実行環境
- 各検出物の信頼度閾値
- 画像1枚あたりの最大ファイルサイズ
- 分類結果を自社サービスへ渡す方式と削除タイミング
- プロトタイプ完成後の自社運用実験の対象物件数と評価期間
- 上限超過時の従量課金額
- 外部事業者向けの認証、アクセス制御、SLA
