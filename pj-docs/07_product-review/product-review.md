# 2. 背景と解決したい課題

不動産会社が撮影する物件写真は、撮影順のまま保管・掲載されることが多い。その結果、顧客は浴室、キッチン、玄関などの見たい場所を一覧から探す必要がある。

また、撮影・入稿担当者には、写真の選別、分類、ファイル名変更、掲載前確認の負担がある。写真枚数が増えるほど、手作業による時間と分類漏れのリスクが大きくなる。

PhotoSortは、物件写真をAIで分析し、顧客が確認したい空間カテゴリへ整理することで、次の状態を目指す。

- 担当者は自動分類後の確認・修正を中心に掲載準備を進められる
- 顧客は見たい場所の写真へ短時間で到達できる
- 不動産事業者は自社の物件検索・物件詳細サービスへの組み込みを検討できる

# 3. 企画上のサービス像

## 想定利用者

| 利用者 | 課題 | 期待する効果 |
| --- | --- | --- |
| 仲介会社の撮影・入稿担当者 | 写真を物件ごと・場所ごとに整理する負担 | 自動分類後の確認・修正で掲載準備を進める |
| 物件管理会社の担当者 | 募集準備や原状確認の写真が混在する | 必要な写真をカテゴリ別に確認する |
| 物件を探す顧客 | 撮影順の一覧から目的の写真を探す | 浴室やキッチンなどの写真へすぐ到達する |

## サービスの基本フロー

1. 1物件分の写真をまとめてアップロードする
2. YOLOが設備・家具などの検出物を取得する
3. JavaScriptが検出物と信頼度をカテゴリへ変換する
4. 担当者が分類結果を確認・手動修正する
5. 将来、自社の物件検索・物件詳細サービスへ表示する

# 4. プロトタイプの目的と範囲

## 今回確認する範囲

- JPG・PNG形式の物件写真の複数アップロード
- YOLOによる検出結果の取得
- 7カテゴリと未分類へのルール分類
- カテゴリ別の写真一覧と判定根拠の表示
- 処理中の進捗・完了・失敗状態の表示
- 担当者による分類先の手動修正
- 処理結果の確認と破棄までの流れ

## 今回対象外

- ユーザー登録、ログイン、権限管理
- 課金、契約、料金計算
- 物件管理システム・不動産ポータルとの自動連携
- 物件写真データによる独自モデルの追加学習
- 物件説明文やキャッチコピーの自動生成
- 長期的な画像保管、個人情報の自動マスキング

# 5. 完成したプロトタイプの成果

## 画面・操作

- 物件識別子を入力して分類対象を特定できる
- 写真単体・複数ファイル・フォルダ単位で写真を追加できる
- ドラッグ&ドロップで写真を追加できる
- JPG、JPEG、PNGを対象に形式を確認できる
- Normal / Proのタブで1回の受付上限を切り替えられる
- 処理済み枚数と写真ごとの処理状態を確認できる
- カテゴリタブとカテゴリ別枚数を確認できる
- 写真プレビュー、ファイル名、分類カテゴリ、検出根拠を表示できる
- 写真ごとに手動修正画面を開き、分類先を変更・保存できる
- 処理結果の確認画面で分類済み・未分類の件数を確認できる
- 不要な処理結果を破棄してアップロード画面へ戻れる

## 技術構成

- 画面: GitHub Pagesで公開可能なHTML / CSS / JavaScript
- 推論API: FastAPIによるローカル推論サーバー
- 推論モデル: Ultralytics YOLOの`yolo11n.pt`
- データ受け渡し: 画像を`/api/infer`へ送信し、検出物・信頼度・矩形をJSONで取得
- 結果保持: 現段階ではブラウザーのセッション内メモリで管理

# 7. 分類ロジックの考え方

分類カテゴリは、YOLOが検出した物体をJavaScriptのカテゴリ対応表へ渡して判定する。

- 複数カテゴリに関係する検出物がある場合は、信頼度スコアを比較する
- 異なる検出物の組み合わせを単独検出より優先する
- 単独検出でもカテゴリ固有性が高く、暫定信頼度を超える場合は分類する
- 根拠が不足する写真は未分類として担当者の確認対象にする
- 担当者の手動修正結果は自動分類より優先する

現行の`yolo11n.pt`はCOCO汎用モデルであり、浴室・玄関・窓などの部屋固有要素を直接分類するモデルではない。そのため、現在のカテゴリ判定は検出可能な家具・設備を用いたプロトタイプ上の近似である。

## 実行確認済み

- Pythonバックエンドの構文チェック
- FastAPI、Ultralytics、Torchの読み込み
- `yolo11n.pt`の読み込み

## プロトタイプで確認する操作

1. 物件識別子を入力する
2. 写真またはフォルダを選択する
3. 分類処理を開始する
4. 処理状況と各写真の状態を確認する
5. カテゴリ別の分類結果を確認する
6. 手動修正画面で分類先を変更する
7. 結果確認画面で件数を確認する
8. 必要に応じて処理結果を破棄する

# 9. 現時点の課題

| 課題 | 影響 | 次の対応 |
| --- | --- | --- |
| `yolo11n.pt`が物件特化モデルではない | 部屋カテゴリの分類精度に限界がある | 自社物件写真で検出率と誤分類を測定し、追加学習を判断 |
| 分類閾値が暫定 | 写真によって未分類・誤分類が増減する | 評価データでカテゴリ別閾値を調整 |
| 結果はセッション内保持 | 再読み込み後に結果を保持できない | 保存方式、保持期間、削除処理を設計 |
| 実ブラウザーのE2E未実施 | 主要操作の回帰を自動検知できない | Chrome/EdgeのPlaywrightシナリオを作成 |
| 性能値が未測定 | 大量写真時の処理時間が不明 | 物件単位の処理時間と失敗率を測定 |
| 公開時のAPI保護が未実装 | 外部公開時の不正利用リスクがある | HTTPS、認証、認可、レート制限を設計 |
| 個人情報対策が未実装 | 顔・表札・ナンバープレート等を含む可能性 | 評価データ管理とマスキング方針を定義 |

# 10. プロトタイプの評価指標

企画書で定めた次の指標を、自社運用実験で測定する。

- 写真整理時間: 手動整理と比較した1物件あたりの完了時間
- 修正率: AI分類後に担当者がカテゴリを変更した写真の割合
- 未分類率: カテゴリを確定できず未分類になった写真の割合
- 顧客の到達性: 指定カテゴリの写真を見つけるまでの時間と操作数
- 処理安定性: 写真枚数ごとの処理時間、失敗枚数、再処理の有無

評価用写真には、可能な限り個人情報を含まない社内利用可能なデータを使用する。

# 11. レビュー判定と次の判断

## 現時点の判定

**プロトタイプとして条件付き達成**

アップロードからYOLO検出、カテゴリ表示、手動修正、結果確認までの一連の画面フローを確認できる状態になった。企画・要件で定めた「分類結果を確認し、手動修正できるプロトタイプ」という目的には到達している。

一方、物件特化の分類精度、保存・連携、公開時のセキュリティ、自動テストは未完了である。本番サービスとしての出荷可否は、このレビューの判定対象外とする。

## 次段階へ進む条件

- 自社物件写真を使った評価データと正解カテゴリを準備する
- 未分類率、修正率、整理時間、処理時間を測定する
- YOLO汎用モデルの継続利用か、物件写真モデルの追加学習かを判断する
- 保存期間、API公開方式、認証・アクセス制御を確定する
